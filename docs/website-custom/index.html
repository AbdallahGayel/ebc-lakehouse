Design Principles

🔀 Storage / Compute Separation
MinIO holds data; Polaris holds the catalog; Trino + Flink are independent compute. Adding Spark = adding a new principal in Polaris, no data movement.
🎯 One Source of Truth
Iceberg is the only place where data lives. Bronze is the latest-state-per-PK CDC mirror; everything downstream is a derivation.
⚡ Streaming-first Ingest
Flink owns the source→bronze edge (sub-minute latency). Airflow + dbt own bronze→serving (hourly). BI users see consistent snapshots.
📝 Schema-on-Write
Avro Schema Registry enforces compatibility on Kafka; Polaris enforces Iceberg schema on Bronze writes; dbt enforces Silver.
🔄 Idempotent Everything
Init scripts, Flink job submissions, dbt models — all are safe to re-run. CREATE IF NOT EXISTS, ON CONFLICT DO NOTHING, MERGE.
🔌 One CDC Pattern Per Source
Three source DBs exercise every Flink CDC variant: logical decoding (Postgres), change stream (Mongo), capture instance (SQL Server).
Data Layers

Medallion Architecture

Data flows through four layers, each with a specific owner, materialization strategy, and maintenance regime.

🥉
BRONZE
Flink

What: Raw mirror of source rows. Upsert mode with equality-field-columns. Latest state per primary key. Continuous writes every 30s checkpoint.

Why: Decouples analytical engines from source DB production traffic. Minimizes CDC overhead and allows downstream schema/logic recovery without re-reading source databases.

🥈
SILVER
dbt-trino

What: Cleaned, typed, deduplicated staging. Incremental MERGE on natural PK + event-time. Hourly refresh via ebc_dbt_silver DAG.

Why: Enforces schema rules, deduplicates events, and casts types. We use an incremental MERGE strategy to process only newly arrived events since the last runs, dramatically optimizing compute costs.

🥇
GOLD
dbt-trino

What: Business-domain aggregates. Full refresh marts — small tables that guarantee exact match with silver. Triggered by silver completion.

Why: Standardizes key metrics (e.g. settlement position). Since Gold tables are small, full table refreshes guarantee consistency with Silver, completely avoiding incremental pipeline sync bugs.

🚀
SERVING
dbt-trino

What: BI-optimized projections. Incremental MERGE on natural BI key. Last-7-day hot window, cache-busting with refreshed_at. Triggered by gold.

Why: Tailored for BI tool query speeds. Limiting the table to a hot 7-day window keeps query latencies low, and the refreshed_at timestamp busts BI client caching.

Layer Contract

Bronze Flink Iceberg Sink upsert (equality-field-columns) Flink compacts on checkpoint Continuous (~30s)

Apache Kafka 3.7
Schema-governed event backbone — KRaft mode, no Zookeeper

Apache Kafka is a distributed, horizontally scalable, partition-based event log. Unlike traditional message queues that delete messages after consumption, Kafka retains all published events on disk according to configuration. Events are written sequentially into partitions, enabling high-performance append-only operations.

Without Kafka, streaming ingestion would require direct source-to-target HTTP or database calls. This tightly couples producers (Flink CDC) with consumers (Iceberg sinks). If Iceberg catalog writes stall or Flink restarts, the source would drop changes. Kafka acts as a highly durable write-ahead log and message buffer, isolating the ingest edge from analytical storage.

ProsCons
Extremely high write throughputSteep operations learning curve
Allows multiple consumers for same topicsRequires strict partition count planning
Durable retention (up to infinity)High memory and disk management overhead

Kafka serves as the central event bus between Flink CDC source jobs and Flink Iceberg sink jobs. Every CDC event from every source database passes through a dedicated Kafka topic before landing in Iceberg.

Key Configuration:

  • Mode: KRaft (no Zookeeper — removed in Confluent ≥ 7.5)
  • Topics: ebc.<schema>.<table> naming convention
  • Partitions: 6 per topic
  • Format: upsert-kafka with avro-confluent serialization
  • Schema Registry: Confluent Schema Registry 7.7 at port 8081
  • Subjects: 10 total (5 key + 5 value schemas)

Apache Flink is a stateful stream processing framework. It is built to run computations over unbounded streams (real-time data) and bounded datasets (batch). Flink keeps state locally in memory or RocksDB and checkpoints that state asynchronously to durable storage for fault tolerance.

Traditional tools like Debezium + Kafka Connect require separate configuration setups for every single table and connector instance, which leads to JSON configuration bloat. Flink CDC unified streaming enables us to define source ingestion and table write sinks through pure, declarative SQL, drastically reducing maintenance overhead.

ProsCons
Stateful EXACTLY_ONCE checkpointsHigh memory usage and strict JVM requirements
Native support for streaming SQLSteep recovery and state tuning curve
Flink CDC 3.0 has schema evolutionRequires running cluster infrastructure

Flink serves a dual role: (1) CDC Source — reads change events from PostgreSQL, MongoDB, and MS SQL Server, and publishes them to Kafka. (2) Iceberg Sink — consumes from Kafka topics and performs streaming upserts into Iceberg Bronze tables via the Polaris REST catalog.

Key Details:

  • Checkpointing Interval: 30s EXACTLY_ONCE
  • State Backend: hashmap (stored in TaskManager heap)
  • SQL Gateway submits queries headlessly to the JobManager

Apache Iceberg 1.7
Open table format — the single source of truth for the entire lakehouse
▼
Category

Apache Iceberg is a high-performance open table format for massive analytical datasets. It acts as a metadata layer on top of raw storage (like Parquet or ORC files), enabling SQL-like transactions (ACID), schema evolution, partition evolution, and historical time-travel queries.

Legacy formats like Hive require scanning entire directories of files to check database changes, which crawls at a snail's pace as data sizes grow. Hive also does not support ACID transactions natively. Iceberg tracks snapshots of datasets at a file level using manifest lists, meaning query engines read data instantly without folder-listing delays.

ProsCons
ACID transactions (readers see consistent view)File write amplification on frequent updates
Schema and partition evolution without rewritesRequires regular compaction and snapshot expiry
Open standard supported by Trino, Spark, FlinkRequires a separate catalog service (e.g. Polaris)

Iceberg is the storage format underlying every table in the lakehouse. It provides the physical file layout inside the MinIO bucket, enabling Flink CDC to write data and Trino to read and query concurrently.

Properties:

  • write.format.default = parquet
  • write.upsert.enabled = true (enables row-level updates)
  • history.expire.max-snapshot-age-ms = 604800000 (7 days retention)

Apache Polaris is a centralized open-source catalog for Iceberg tables. It exposes the standardized Iceberg REST catalog API, allowing different query engines (like Flink, Trino, and Spark) to securely discover and read tables without hardcoding individual credentials.

Without Polaris, each compute engine would require direct admin keys to S3/MinIO and its own manual copy of table metadata. This presents massive security risks and leads to out-of-sync table state. Polaris centralizes access control, issuing short-lived vended credentials scoped only to the specific table directories being queried.

ProsCons
Centralized OAuth2 catalog securityRelatively new project in the Iceberg ecosystem
Vends scoped, short-lived S3 access tokensRequires running an extra database backend for states
Compatible with any Iceberg REST clientFewer built-in UI administration tools currently

Polaris manages the ebc_lakehouse catalog and namespaces. Flink and Trino talk directly to Polaris at port 8181 to check schema changes and metadata paths, fetching vended storage credentials on demand.

MinIO is a high-performance, S3-compatible object storage server. It stores unstructured data, files, and objects securely. It is designed to run locally on containerized systems or scale horizontally across massive distributed environments.

Testing cloud-native S3 pipelines locally requires expensive AWS sandboxes, which incur data transfer costs and demand active internet connections. MinIO replaces AWS S3 completely for local development, allowing developers to run identical S3-based ingestion jobs offline with zero costs.

ProsCons
Full S3 API compatibilityRequires self-management of storage volumes
Extremely fast local file operationsNo built-in global replication like AWS S3
Resource-light and easy to configureData safety depends entirely on local hardware

MinIO serves as the physical storage layer of the EBC Lakehouse. Flink writes Parquet files to MinIO, and Trino scans them via metadata instructions. Bucket location: s3://ebc-lakehouse/.

Trino (formerly PrestoSQL) is a fast, distributed SQL query engine designed to query large-scale datasets across one or more heterogeneous data sources. It compiles ANSI SQL queries into distributed execution plans, executing them in parallel across a cluster of worker nodes entirely in memory.

Standard SQL databases struggle to scale to petabytes of data, and traditional MapReduce systems (like Hadoop Spark) introduce massive start-up latencies (often taking minutes to launch simple count queries). Trino solves this by processing SQL queries directly in-memory, returning results from object stores in milliseconds.

ProsCons
Extremely fast, memory-optimized SQLHigh memory consumption; prone to Out-Of-Memory
Queries data where it lives without ETLNo built-in storage; query engine only
Federated query capabilities (joins S3+Postgres)Requires separate caching setups for BI efficiency

Trino acts as the query engine for dbt transformations, ad-hoc analyst SQL queries, and the Superset dashboard. It reads metadata from Polaris, fetches Parquet files from MinIO, and processes joins and aggregate calculations.

dbt (data build tool) is a development framework that enables data teams to write, compile, and run SQL transformations. It brings software engineering practices—like version control, modular modularization, testing, and continuous integration—to analytics code.

Traditional SQL transformations are written as monolithic, multi-thousand-line stored procedures or shell scripts that run in sequence on database schedulers. These scripts are hard to test, document, and debug. dbt solves this by compiling modular SQL files, automatically managing table dependencies, and providing data tests.

ProsCons
Automated dependency graph (DAG) resolutionRequires a separate scheduler (like Airflow)
Built-in testing frameworks (null, unique, SLA)SQL-only; not suited for complex procedural logic
Generates automated documentation with lineageTends to create massive numbers of staging models

dbt-trino coordinates transformations from Bronze to Silver, Gold, and Serving layers inside Iceberg. It compiles models and triggers them sequentially via Trino.

Apache Airflow is an open-source platform to programmatically author, schedule, and monitor workflows. Workflows are declared as Directed Acyclic Graphs (DAGs) in Python code, which are read by the Airflow scheduler and distributed to workers for execution.

Relying on cron jobs for orchestration is fragile because cron lacks dependency tracking (e.g. if Step A fails, cron still runs Step B). Cron also lacks centralized logging, job retries, and failure alerts. Airflow resolves this by providing a unified UI to monitor task execution, manage failures, and handle complex routing logic.

ProsCons

Extensive operator library (Trino, dbt, Slack)Python environment version matching issues

Airflow schedules and coordinates the execution of dbt models (Silver -> Gold -> Serving). It also manages regular Iceberg metadata maintenance tasks (compaction and snapshot expiration).

Schema Registry is a metadata repository for schema serialization (like Avro, Protobuf, or JSON Schema) in event brokers. It provides a RESTful interface to register and fetch schemas, enforcing data types at topic entry points.

Without schema enforcement, any database change on sources (e.g. dropping columns or changing types) reaches Kafka topic events as unreadable text. This crashes downstream decoders (Flink sinks). Schema Registry acts as a gatekeeper, rejecting incompatible messages before they corrupt the event stream.

ProsCons
Prevents bad schemas from entering topicsSingle point of failure for message writing/reading
Reduces message payload sizes (saves bytes)Fewer debugging tools for binary Avro payloads
Supports evolution rules (backward/forward compatibility)Adds complexity to local dev serialization setups

Schema Registry governs Avro schemas for all 5 Kafka topics. The Flink CDC write edge uses it to register schemas and append binary schema ID tags to event payloads.

PostgreSQL is a powerful, open-source object-relational database system. It supports relational (SQL) and non-relational (JSON) querying, and uses logical replication slots to publish database change events.

Reading changes from transactional tables using periodic SELECT queries requires querying date columns constantly. This slows down database operations, locks tables, and completely misses intermediate row deletions. PostgreSQL logical replication (WAL) broadcasts row-level changes immediately with zero query overhead.

ProsCons
ACID compliant transactional storageWrite-Ahead Logs (WAL) can fill disk if slots stall
Native replication slot support for CDCLogical decoding slot management requires admin permissions
Reliable indexing and query plannerReplication streams can lag under heavy bulk writes

PostgreSQL acts as the transactional source DB for ACH transactions, Meeza authorisations, and IPN transactions. Flink CDC connects to its WAL logical slot to capture change events.

MongoDB is a document database designed for ease of development and scaling. It stores data in flexible, JSON-like document structures. It uses a replication oplog to sync state across replica sets, which can be tapped as an event source.

Parsing nested event logs in NoSQL stores requires writing custom polling scripts that constantly poll collections. This locks threads and misses document updates/deletes. Workflows

Data Flow & Bootstrap

The step-by-step transaction life cycle, bootstrap order, and Airflow DAG coordination.

1️⃣ Step-by-Step Payment Event Lifecycle

Here is what happens to a single transaction—from the moment it's inserted into the source PostgreSQL database until it updates a Superset BI chart:

1
Database Insert (PostgreSQL Source)
A customer initiates an ACH bank transfer. PostgreSQL commits the transaction row, appending logical replication records to the database Write-Ahead Log (WAL).
2
Logical CDC Capture (Flink Source)
The Flink CDC 3.2 source job captures the WAL update stream in real-time, deserializes the raw bytes, and registers/updates the schema definitions.
3
Avro Serialization & Publish (Kafka Topic)
Flink serialized the change event as binary Avro (governed by the Confluent Schema Registry) and publishes it to the ebc.public.ach_transactions topic on Kafka (6 partitions).
4
Topic Streaming & Sink (Flink Sink)
The corresponding Flink Iceberg sink job reads from the Kafka topic and writes data files (Parquet with row-level deletions) into S3 storage (MinIO) at 30-second intervals.
5
Catalog Transaction Registry (Polaris REST)
On checkpoint completion, Flink registers table commit records in the Apache Polaris Catalog using temporary vended storage tokens. The new rows are now visible to readers.
6
Incremental Deduplication (dbt-trino Silver)
Airflow's ebc_dbt_silver DAG runs hourly, executing dbt models on Trino. Trino issues an SQL MERGE INTO statement to deduplicate Bronze rows and load Silver staging tables.
7
Analytical Aggregations (dbt-trino Gold & Serving)
Subsequent triggered DAGs compile Gold aggregates (e.g. daily totals) and Serving models. Tables are optimized and old metadata snapshots expired.
8
BI Dashboard Refresh (Superset & Trino)
An executive loads the settlement dashboard. Apache Superset queries Trino, which scans the Serving layer's latest Iceberg data in MinIO, displaying the updated transfer aggregates in seconds.

2️⃣ System Bootstrap Order

scripts/init_all.sh enforces this exact sequence. Respect this order if running manually.

1
Kafka (KRaft) → Schema Registry
Start the event backbone first. Kafka boots in KRaft mode (no Zookeeper). Schema Registry connects and becomes ready to accept Avro schema registrations.
2
MinIO → MinIO Init
Start object storage and create the ebc-lakehouse bucket. This provides the physical storage layer for all Iceberg data.
3
Polaris Postgres → Bootstrap → Polaris → Catalog Init
Start Polaris's backing Postgres, bootstrap the Polaris realm, start the Polaris service, then create the ebc_lakehouse catalog with bronze/silver/gold/serving namespaces and OAuth2 principals.
4
Trino → Trino Init
Start Trino with the Iceberg connector pointing to Polaris. Create schemas and serving DDL (including pipeline_metrics table).
5
Postgres Meta → Airflow Init → Scheduler + Webserver
Start the Airflow metadata database, run migrations, create the admin user, then start the scheduler and webserver. DAGs are now available.
6
Flink JM → TM → SQL Gateway → Init (first pass)
Start the Flink cluster (JobManager + TaskManager + SQL Gateway). Submit all jobs for the first time. CDC source jobs won't find sources yet — this is expected.
7
Source DBs: postgres-src / mongodb / mssql
Start the three source databases with seed data. PostgreSQL seeds ACH/Meeza/IPN, MongoDB seeds wallet events, SQL Server seeds ATM sessions.
8
Flink Init (re-submit)
Re-submit all Flink jobs now that sources are reachable. CDC connectors attach and begin streaming. The submitter cancels matching prior jobs before re-submitting (idempotent).
9
DataHub MySQL / ES → GMS → Upgrade → Frontend / Actions
Start DataHub's backing stores, then GMS (metadata service), run schema migration, then start the frontend UI and actions framework (ingestion recipes).
10
Redis → Superset Init → Superset + Worker
Start Redis (Superset cache), bootstrap Superset (create admin, register Trino database), then start the Superset web server and Celery worker.

Glossary

Key terms and concepts used throughout the EBC Lakehouse platform.

Bronze Layer
Raw mirror of source rows in Iceberg, written continuously by Flink. Latest state per primary key, with zero analytical cleaning or schema transformations.
Silver Layer
Cleaned, typed, and deduplicated staging layer, owned by dbt. Employs an incremental MERGE strategy based on natural keys and event-time ordering.
Gold Layer
Business-domain aggregates — full-refresh marts that guarantee exact match with Silver. These represent the primary analytical tables.
Serving Layer
BI-optimised, MERGE-upserted projections of Gold with cache-busting timestamps. Contains a rolling hot window of data for instant dashboard queries.
CDC (Change Data Capture)
Streaming row-level changes from a source database. PostgreSQL uses logical replication (WAL), MongoDB uses change streams, and MS SQL Server uses Agent capture tables. Cross-links: PostgreSQL, MongoDB, MS SQL Server.
upsert-kafka
Flink connector that treats a Kafka topic as a compacted, key-value table, sending updates or deletes based on primary keys. Cross-link: Apache Kafka.
equality-field-columns
Iceberg sink properties mapping primary keys that Flink uses to identify and update records during streaming upserts. Cross-link: Apache Iceberg.
Polaris
Apache Iceberg REST catalog exposing standardized OAuth2 credentials and vending temporary S3 storage paths. Cross-link: Apache Polaris.
Vended Credentials
Polaris-issued, short-lived S3 credentials that scope catalog client permissions to specific storage prefixes.
MERGE Strategy
An incremental write strategy in dbt-trino that executes SQL MERGE INTO against target Iceberg tables, performing updates and inserts efficiently.
TaskGroup
Airflow construct that groups related tasks in the webserver UI to visually simplify graph monitoring without altering logic dependencies.
KRaft
Kafka Raft metadata mode that replaces Zookeeper, simplifying cluster coordination and improving partition scaling limits.
EXACTLY_ONCE
Flink's execution guarantee that uses checkpoints to ensure stream records are processed and committed exactly once in sinks, avoiding duplicates.
Snapshot Expiry
Iceberg metadata maintenance task that deletes old database snapshots and their associated data files on S3 to recover storage.
Optimize
Iceberg metadata operation that compacts small Parquet files into larger files, improving downstream read speeds.
OpenLineage
Open API standard for metadata collection. Airflow sends OpenLineage payloads to DataHub to render runtime column and table dependencies.
WAL (Write-Ahead Logging)
A family of techniques for providing atomicity and durability in database systems. PostgreSQL logical CDC reads events straight from WAL slots.
ACID Transactions
Atomicity, Consistency, Isolation, and Durability guarantees. Iceberg brings ACID transactional safety to object storage files.
Schema Registry
Central repository governing Avro schema definitions. Enforces serialization rules on Kafka producers and consumers. Cross-link: Schema Registry.
OpenLineage Bridge
Custom Python daemon translating incoming OpenLineage payloads from Airflow into DataHub-compatible GraphQL ingestion APIs.
Vending Catalog
A catalog structure where metadata queries return temporary object storage paths and scoped access tokens to clients, isolating physical storage credentials.

Sample Trino Queries

sql
-- Daily transaction volume across all rails
SELECT report_date, scheme, txn_count, total_amount_egp
FROM   iceberg.serving.daily_txn_volume
WHERE  report_date >= current_date - INTERVAL '7' DAY
ORDER  BY report_date DESC, scheme;

-- IPN SLA compliance
SELECT count(*)                                       AS total_txns,
       count_if(met_sla)                              AS met,
       round(count_if(met_sla) * 100.0 / count(*), 2) AS pct
FROM   iceberg.silver.stg_ipn_transactions;

-- ATM uptime by network
SELECT network_id, count(*) AS sessions,
       count_if(txn_status = 'APPROVED') AS approved
FROM   iceberg.silver.stg_atm_sessions
GROUP  BY network_id;

-- Settlement net position (bank to bank)
SELECT originating_bank_id, receiving_bank_id,
       net_settled_egp, settlement_rate_pct
FROM   iceberg.serving.settlement_summary
WHERE  settlement_date = current_date - INTERVAL '1' DAY
ORDER  BY net_settled_egp DESC
LIMIT  20;

-- Iceberg snapshot history
SELECT committed_at, snapshot_id, operation, summary
FROM   "iceberg.bronze.ach_transactions$snapshots"
ORDER  BY committed_at DESC
LIMIT  10;

Troubleshooting

Silver DAG fails on check_bronze_freshness
▼

Symptom: Bronze freshness FAILED: bronze.X: lag 6.2h exceeds 6h SLA…

Cause: No source-side activity for more than EBC_BRONZE_SLA_HOURS (default 6h).

Fix:

bash
# Option A: Generate traffic
bash scripts/generate_continuous_traffic.sh

# Option B: Raise the SLA temporarily
# Edit EBC_BRONZE_SLA_HOURS in compose/docker-compose.core.yml

Tables idle > 24h (EBC_BRONZE_HISTORICAL_HOURS) are treated as backfills and warn rather than fail.

Flink jobs FAILED: NoResourceAvailableException
▼

Cause: TaskManager slot exhaustion. Default is 16 slots; each running job consumes 1.

bash
# Check slot usage
curl -s http://localhost:8881/overview | python -m json.tool | grep slots

# Fix: bump taskmanager.numberOfTaskSlots in core compose, then:
docker compose -f compose/docker-compose.core.yml up -d --no-deps \
    --force-recreate flink-taskmanager
bash scripts/init_flink.sh
Flink Iceberg sink commits 0 rows to Iceberg
▼

Cause: Checkpointing not enabled in the SQL Gateway session. Iceberg sink only commits on a successful checkpoint.

Fix: The submitter (scripts/flink/submit_flink_jobs.sh) already sets checkpointing. If you ran jobs manually, add these session properties:

json
{
  "execution.checkpointing.interval": "30s",
  "execution.checkpointing.mode": "EXACTLY_ONCE",
  "state.backend.type": "hashmap",
  "state.checkpoints.dir": "file:///tmp/flink-checkpoints"
}
Trino: Access Denied — Cannot execute query
▼

Cause: Using a user not in trino/etc/rules.json.

Fix: Use an allowed user: root, ebc_admin, ebc_user, ebc_engineer, or ebc_bi.

bash
docker exec -e JAVA_TOOL_OPTIONS= ebc-trino \
    trino --user ebc_user --catalog iceberg --schema bronze \
    --execute "SELECT COUNT(*) FROM ach_transactions"
Bronze tables stay empty
▼

Check in this order:

bash
# 1. Source DB has rows?
docker exec ebc-postgres-src psql -U ebc_src -d ebc_sources \
    -c "SELECT COUNT(*) FROM ach_transactions"

# 2. Flink CDC source job RUNNING?
curl -s http://localhost:8881/jobs/overview | grep -A1 kafka_ach_sink

# 3. Kafka topic has messages?
docker exec ebc-kafka kafka-get-offsets --bootstrap-server localhost:29092 \
    --topic ebc.public.ach_transactions

# 4. Flink Iceberg sink job RUNNING + checkpointing?
curl -s http://localhost:8881/jobs/overview | grep polaris.bronze.ach
Full reset — re-bootstrap the entire data plane
▼
bash
docker compose down -v                    # delete all volumes
docker network rm ebc-lakehouse-network   # delete the bridge
bash scripts/init_all.sh                  # full clean rebuild

This is the only reliable way to recover from a corrupted Polaris realm or a Kafka cluster ID mismatch.

Onboarding Guide

A step-by-step developer checklist for local setup, running diagnostics, and adding analytics logic.

🚀 Quick Start Checklist

Follow this sequence to spin up and verify your local EBC Lakehouse replica:

  • Clone the repository and ensure your Docker engine has at least 12 GB of RAM allocated.
  • Run bash scripts/init_all.sh to bootstrap all core, source, and governance containers.
  • Verify all 10 Flink CDC and Iceberg sink jobs are running at the Flink Dashboard.
  • Trigger the dbt medallion pipeline: docker exec ebc-airflow-webserver airflow dags trigger ebc_dbt_silver.
  • Run bash scripts/verify.sh to confirm matching row counts across Bronze, Silver, Gold, and Serving namespaces.

📊 Querying the Lakehouse

Query all Iceberg layers interactively using the Trino SQL CLI:

bash
# Launch Trino CLI session
docker exec -it ebc-trino trino --user ebc_user --catalog iceberg --schema serving

# Check daily transaction aggregates
trino:serving> SELECT * FROM daily_txn_volume LIMIT 5;

🔧 How to Add a New dbt Transformation Model

  1. Create your model SQL file inside the target directory: dbt/ebc_lakehouse/models/<layer>/<model_name>.sql.
  2. Reference source tables using the ref macro: FROM {{ ref('stg_ach_transactions') }}.
  3. Run transformations locally through Trino using docker: 
    docker exec -it ebc-airflow-webserver dbt run --select <model_name> --profiles-dir /opt/airflow/dbt
  4. Add schema tests in the layer's schema.yml to audit unique keys and null violations.
